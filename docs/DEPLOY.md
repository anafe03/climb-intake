# Running and deploying it

Everything you need to bring the service up, plus what to say when someone asks about the
container. Written to be read cold, five minutes before a demo.

## The three commands

```bash
docker compose up -d --build     # build the image and run it on :8080
open http://localhost:8080       # the app
docker compose down              # stop it; add -v to wipe the audit volume too
```

That is the whole local story. There is no separate dev setup to learn: the container is what runs
in the demo and the same image is what would go to Cloud Run.

Useful while it is up:

```bash
docker compose logs -f intake            # one JSON line per decision
docker compose ps                        # STATUS says (healthy) once /health passes
curl -s localhost:8080/health | jq       # which mode and model it is actually on
```

## Is it up, or is it up and degraded?

`/health` answers both. `ok` is false when a key is configured but the last model call failed —
the service keeps serving in that state, on the keyword rules, so a plain 200 would hide a real
degradation. The badge in the top right of the app reads the same endpoint.

```json
{"ok": true, "mode": "llm", "provider": "openai", "model": "gpt-5", "last_model_call": "ok"}
```

`mode: rules` means no key was found. Every endpoint still works; the answers come from the
keyword classifier alone.

## What is in the image, and why

| Choice | Reason |
|---|---|
| `python:3.12-slim` | Small, and the app has no system dependencies worth a bigger base. |
| `requirements.lock` copied and installed **before** the app | Dependencies are their own layer, so an app edit rebuilds in seconds instead of reinstalling the world. |
| A lockfile rather than `pyproject.toml` ranges | Two builds a month apart produce the same image. Generated by `uv pip compile`. |
| `USER climb` (uid 10001) | Nothing in the container needs root. Cloud Run will not stop you running as root; that is not a reason to. |
| `HEALTHCHECK` in the image | The orchestrator gets the same signal locally as in the cloud, rather than each learning health separately. |
| `PORT` read from the environment | Cloud Run injects `PORT`. Hard-coding 8080 is the single most common reason a container that works locally will not start there. |
| Audit DB on a named volume | Decisions survive `docker compose restart`. `down -v` is the deliberate reset. |

## Secrets

`.env` is gitignored and has never been committed. Compose reads it with `env_file`, so keys reach
the container as environment variables and are never baked into an image layer. `.env.example`
documents every variable with no values in it.

In the cloud the same variables come from Secret Manager, injected by Cloud Run at start. The
service account is scoped to read those secrets and nothing else in the project.

## Deploying it

Infrastructure is in [../infra/terraform](../infra/terraform) — eight resources: the Artifact
Registry repo, a Secret Manager secret and version per provider key you pass, a service account,
the IAM binding letting that account read those secrets, the Cloud Run v2 service, and the public
invoker binding.

```bash
gcloud auth login && gcloud config set project $PROJECT
PROJECT=$PROJECT ./scripts/deploy.sh      # OPENAI_API_KEY from the env or .env
```

[scripts/deploy.sh](../scripts/deploy.sh) does it in the order that works from a clean project:
`tofu apply` for the APIs and the registry alone, then `docker buildx build --platform linux/amd64
--push` (Cloud Run is amd64-only, and an image built plainly on an Apple Silicon Mac is arm64), then
the full `tofu apply`, then a `/health` check against the URL. The key reaches Terraform as
`TF_VAR_openai_api_key`, so it never appears on a command line.

Either provider works: pass `openai_api_key`, `anthropic_api_key`, or both and let
`llm_provider` choose. Only the keys you pass get a secret created.

**Honest status:** the configuration validates under OpenTofu 1.x against the current `google`
provider. It has **not been applied** — there is no GCP project or `gcloud` on this machine.
Expect to iterate once on `tofu plan`. Say that plainly if asked; it is a smaller problem than
claiming a deploy nobody ran.

## What would change for real traffic

In the order I would actually do them:

1. **Drop the public invoker binding.** `-var public=false` and put IAP or an API gateway in
   front. It is open now because a demo URL that needs auth is not a demo.
2. **Move the audit store off SQLite.** It is behind the `app/audit.py` interface precisely so
   this is a swap, not a rewrite. Cloud SQL Postgres, same calls.
3. **Make intake async.** Cloud Tasks or Pub/Sub in front of `POST /tickets`, so a slow model call
   cannot hold an HTTP connection open and a retry is the queue's job rather than the caller's.
4. **Batch the backfill path.** Anything over a few hundred tickets belongs on the provider's
   batch API, not on the synchronous endpoint.

The AWS shape is the same three pieces: App Runner, Secrets Manager, ECR.

## If it will not start

| Symptom | Cause |
|---|---|
| `ports are not available: 8080` | Something else has the port. `lsof -i :8080`, or change the left-hand side of the compose port mapping. |
| Container restarts in a loop | Read `docker compose logs intake`. Almost always a bad `.env` line, since compose passes it through verbatim. |
| `Cannot connect to the Docker daemon` | The VM is not up. `colima start` on this machine. |
| App loads but every ticket is `mode: rules` | No key reached the container. `docker compose exec intake env \| grep -c API_KEY`. |
| The page looks stale after an edit | You rebuilt without recreating. `docker compose up -d --build`, then `diff <(curl -s localhost:8080/) app/static/index.html`. |
