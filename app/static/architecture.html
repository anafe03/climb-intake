The pipeline

Why the guardrail can only push one way

Urgency, escalation and review are three different dials

This is the thing most worth being precise about, because one label can teach the wrong model of the system. Urgency is speed. Escalation is topic. Human review is uncertainty.

RouteTriggered byWhat it means
Its own team's queuealwaysEvery ticket lands somewhere a person works. There is no "nobody sees this" outcome.
On-call, paged nowurgency is criticalSame team, woken up. A checkout bug double-charging customers goes here within minutes.
Escalation desk, on top of its teamsecurity, legal/contract, compliance, executiveSomeone outside the owning team needs to know. The ticket is copied, never moved.
Human review, instead of a teamcategory confidence under 0.50The classifier was too unsure to pick a team, so a person picks instead.

"Does high enough urgency get escalated?"

No, and that is deliberate. A checkout bug double-charging 1,900 customers is as urgent as this system gets. It is critical, it pages engineering on-call, and it does not escalate — because escalation is about who else needs to know, not how bad it is. Engineering owns a product defect. Nobody outside engineering needs to be pulled in to own it.

If severity escalated things, the escalation desk would receive every outage and stop being a signal. And the inverse case proves the point: a CEO writing to say thank you escalates at low urgency. Nothing needs doing quickly; somebody senior just needs to know.

"The security team already gets it — why flag it as well?"

Because routing and flagging answer different questions. Routing asks who handles this. The flag asks did we catch it. A security ticket goes to security-incident-response the same way a billing ticket goes to billing. The flag is a separate signal on top.

How much the flag adds depends on who owns the ticket, and it is worth being honest about that:

Owning teamWhat the escalation flag adds
SecurityMostly governance, not handling. Security will treat it as an incident regardless. What the flag buys is countability: a ticket sitting in the security queue looks identical whether it is a real breach or someone asking where the SOC 2 report lives. Without the flag, "how many escalations did we get, and did we miss any" has no answer.
Anyone elseIt is the only signal. An executive mention on an onboarding ticket routes to customer success, who would work it as ordinary onboarding. Nobody senior would ever learn that a CEO is watching. Same for a legal threat arriving as a billing question. Here the copy to the escalation desk is the entire point.

So: for security it is belt-and-braces plus an audit trail. For everything else it is the mechanism. One rule covers both, which is why it applies uniformly rather than being special-cased per category.

Where the brief's wording lands "Flag anything that looks like it needs human escalation (security issues, legal/contract threats, executive mentions)" names three topics, not a severity threshold. That sentence is the reason escalation is modelled as a topic and urgency as a separate scale.

The bug / security boundary

This is the hardest line to draw, and it is worth drawing because the two categories route to different teams and only one of them escalates. A vulnerability is a defect; a permissions leak is a defect. Deciding on "is something broken" would put everything in one bucket.

So the rule is what kind of harm, not whether something is broken:

If the harm is…CategoryBecause
the wrong person can see or do somethingsecurityaccess, credentials, exposure, a tenant boundary crossed — even when the cause is plainly a code defect

That is what the split is for: the genuinely ambiguous tickets are visibly ambiguous instead of being rounded off.

What the model is asked for

One call per ticket, with a schema it must fill. Every field carries its own reasoning, because the question a reviewer actually asks is "why did you decide that", not "why this ticket".

FieldWhat the prompt asks for
customerName only if stated verbatim. Separately, a best guess with a confidence score and the cues it rests on. A guess never enters the name field.
categoryOne of eight, plus the runner-up categories and their share. Confidence is framed as if ten support leads read this, how many file it here.
urgencyNever stated, always inferred — from deadlines, financial size, scope, recurrence, and whether harm is ongoing. Tone is explicitly not urgency.
escalateFive topics, each defined. The prompt says the cost of a miss is far higher than the cost of a false positive.
reasoningOne per field. The category reason must name the alternative it rejected; the escalation reason must name the topics it ruled out.

Ticket text is wrapped in tags and declared as data, never instructions. A gold-set row is a prompt injection attempt that must still land in a real queue.

What gets written down

Every decision produces a SQLite row and a JSON line on stdout. The record keeps both answers — what the model said and what shipped after the guardrails ran — plus every rule that fired with the exact text it matched, token counts, latency, and which mode produced it.

The test that matters If a customer asks in March why their February ticket went where it went, the answer is a row, not an archaeology project.

Where it breaks

The gold set reports 100% escalation recall with zero false escalations, in both modes. That is a suspicious number and quoting it is not an answer. So there is a second set built to defeat the thing — twelve tickets, each naming the attack it makes. A failing row there is the output, not a defect.

On 12 adversarial ticketsModel pathKeyword rules alone
Missed escalationsnone3 — adv-05, adv-06, adv-11

It still never misses an escalation, and that is the number that matters. What it does instead is over-escalate, in four situations where the vocabulary of an incident appears without the incident:

TicketThe trapWhat happened
adv-01Negation — "we have NOT had a data breach" Escalated. See below; this one is the interesting failure.
adv-02Hypothetical — "if we ever found a vulnerability, what is your process?" Escalated. Arguably right: a disclosure-process question from a security team may be worth a look.
adv-03Third party — a competitor's lawyer, nothing to do with us Escalated on the word lawyer.
adv-12Figurative — "a total breach of trust" Escalated. The phrase is in the legal pattern; the meaning is not legal at all.
adv-01 is the one to look at, because the model got it right and the guardrail broke it The model read the ticket correctly — other, medium urgency, no escalation, with the reasoning "they explicitly state no breach… this is a routine SOC 2 request". Then the keyword layer matched the literal string data breach inside the denial, forced escalate=true and lifted urgency to critical. The shipped answer is worse than the model's answer.

That is not a bug to be fixed quietly. It is the asymmetry working exactly as designed — the rules may only raise, never lower, and a regex cannot read a negation. The cost of never missing an escalation is that a denial of one gets escalated. The audit record shows both answers and both overrides by name, so the mistake is legible rather than mysterious, and a reviewer clears it in seconds.

The keyword layer on its own fails the other way, which is the argument for having both: adv-05 (a cross-tenant leak described as "probably nothing"), adv-06 (credentials written as cr3ds) and adv-11 (the same incident in Spanish) are all invisible to it. The model caught every one. Full transcripts in docs/STRESS-llm.md and docs/STRESS-rules.md.

What it costs, and why not a cheaper model

Every decision carries its own price, computed from the tokens the provider actually reported and the rate card in app/pricing.py. Open any ticket and the cost is on the footer line next to the token counts. At 0.9¢ a ticket, a thousand tickets is about $9.

So the honest question is not whether this is affordable. It is whether something cheaper would do. Same prompt, same schema, same guardrails, 33 gold tickets — only the model and its reasoning effort change:

Read the error columns, not the cost column. Three things fall out of this table that an accuracy score would have hidden completely:

Nobody missed an escalation. That is the column that would disqualify a model outright, and every row passes — partly because the keyword layer sits underneath all of them and would have caught it anyway.

Cheaper models buy their discount in false escalations. Mini over-escalates the SOC 2 document request — a procurement question that reads like a compliance demand. That is a tolerable error: a person spends a minute on it. But it is the price of the 5× saving and it should be quoted alongside it.

Nano is disqualified, and it scores 100% on category. It read three critical tickets as high, one of them a provided sample — the checkout flow double-charging customers. Those tickets sit. That is the failure this system exists to prevent, and a model can be 26× cheaper, perfectly accurate on category, and still unusable because of it.

Why the cheap model gets worse when you give it less thinking Dropping mini from low to minimal reasoning effort saved 31% and tripled its false escalations, from one to three. Less thinking does not degrade a classifier evenly; it makes it reach for the alarming answer. Cost and caution are the same dial.

Making a cheaper model good enough

The model is the lever people reach for first. It is the third-best one here.

LeverEffectWhat it costs
Prompt caching ~90% of input tokens are cache reads, at a tenth of the price Nothing. The system prompt is a stable prefix, so it is free after the first call warms it.
Reasoning effort The dominant output-token lever. Moving to low roughly halved output tokens. Judgment on the hard rows — see the note above.
A smaller model 5× to 26× cheaper The error profile changes shape, not just magnitude.
Cascade Pick the reader per ticket. Measured below: 38% cheaper when the keyword layer does the triage, 29% more expensive when a cheap model does. Complexity, and the cheap model's error profile on the tickets it handles.

The cascade is the one worth building if volume ever justified it, and the code is already shaped for it. The confidence threshold that sends unsure tickets to human-review is the same signal that would send them to a better reader instead: everything under 0.50 goes to the expensive model, everything above ships on the cheap one. That is a routing change in app/routing.yaml and one branch in the pipeline, not a redesign.

I built the cascade. The obvious version loses money.

Worth showing because the arithmetic looks fine right up until you measure it. Draft every ticket on gpt-5-mini, then re-read on gpt-5 when the draft escalates, calls it high or critical, or is unsure. 58% got re-read, so the naive sum says about 22% saved.

Why the draft version loses: adverse selection The tickets a cascade chooses to re-read are, by construction, the hard ones — they escalate, or they are urgent. A hard ticket costs nearly double the average on the expensive model: 1.73¢ against a 0.91¢ average. So the draft is pure overhead on most of the spend, and the saving never arrives. It is invisible if you reason about an average cost per ticket instead of pricing each one.

The version that works does the triage for free. The keyword layer already reads every ticket — it is the guardrail. Let it choose the reader instead of paying a model to choose: anything that trips an escalation pattern, or reads as high urgency on keywords alone, goes to gpt-5; everything else goes to gpt-5-mini. One model call either way. 17 of 33 tickets took the expensive path, and the bill fell 38%.

What it costs is mini's error profile on the half it handles: one false escalation, the SOC 2 document request again, and one low-versus-medium urgency disagreement. Nothing was missed and no critical ticket was under-called, which are the two results that would rule it out. Enabled with LLM_CASCADE=1 CASCADE_TRIAGE=rules; off by default, because at this volume 0.9¢ a ticket does not need optimising and the simpler system is the one I would hand over.
